# Производительность Breakly

## Методика

Измерения выполнены 15 ноября 2026 на реальной Windows 11 Pro 25H2, build 26200, x64, 16 логических процессоров. Release MSVC `/O2`, `/MT`, оптимизация компоновки. Сценарий создаёт изолированный профиль, не меняет автозапуск и не смешивает счётчики с пользовательским экземпляром. Интервалы тестового профиля увеличены до суток, режим чтения включён: учёт активности работает, новые напоминания не мешают ожиданию.

«Холодный запуск» в таблицах означает новый процесс без ранее открытого интерфейса, а не принудительно очищенный файловый кэш Windows. Кэш ОС и другие программы не отключались. Время до трея фиксируется только после успешного NIM_ADD. Внутреннее время начинается с конструктора App; внешнее включает запуск процесса и задержку обнаружения диагностического файла. Для абсолютного первого запуска после перезагрузки повторите сценарий после перезагрузки Windows.

- **Private Working Set**: QueryWorkingSet, сумма резидентных страниц с `Shared=0` × размер страницы. Это не общий Working Set и не Private Bytes.
- **Private Bytes**: Process.PrivateMemorySize64, выделенная частная память, включая нерезидентную.
- **CPU**: разница TotalProcessorTime / реальный интервал. Основной столбец нормирован на все 16 логических процессоров; CSV также содержит процент относительно одного ядра. CPU ожидания усреднён за полные пять минут. Для остальных этапов — за интервал между снимками, обычно около двух секунд; квант учёта CPU Windows ограничивает точность коротких измерений. Нулевое значение означает отсутствие зарегистрированного кванта, а не абсолютное отсутствие вычислений.
- **Threads**, GDI/USER и handles: свойства процесса и GetGuiResources.
- Все числа памяти ниже указаны в МиБ (1 048 576 байт). Исходные CSV содержат байты, UTC-метки и счётчики без округления.

## Итоговый Release x64

Поставка: **один Breakly.exe, 426 496 байт (416,5 КиБ; 0,407 МиБ)**. Системные DLL в поставку не копируются. Зависимости проверены dumpbin: только Windows DLL, без .NET и внешнего VC Runtime. Полный список поставки: `measurements/final-exact/delivery.csv` (пересчитан по `dist`, а не по папке сборки с тестами).

Готовность трея: **63,6404 мс** снаружи процесса; **6,5853 мс** внутри App до успешного Shell_NotifyIcon. Это одна наблюдаемая загрузка, без оценки p95 и без очистки файлового кэша.

Измерялся `out/Release/Breakly.exe`; его SHA-256 совпадает с поставляемым `dist/Breakly.exe`: `4C0AFE2F3DFC3CFEFBAA6A936694127C291F1346EA6E22127B617C1352F007E0`.

Пятиминутное ожидание: **0,000326% CPU** всех ядер (**0,005208%** одного ядра), Private Working Set **1,504 МиБ**. После 60 циклов закрытых окон — **9,129 МиБ**. В этих измерениях достигнуты цели размера, фоновой памяти, среднего CPU и времени запуска. Метрики других компьютеров могут отличаться.

После прогрева количество GDI осталось 16, USER — 12–13, handles — 196–197; роста на каждом цикле не обнаружено. Сырые данные: `measurements/final-exact/metrics.csv`, параметры и хэш: `environment.json` в той же папке.


## Найденное узкое место

В аппаратном пути Direct2D маленькие окна создавали GPU-контексты и загружали кэши драйвера: Private Bytes открытого уведомления достигали 50,4 МиБ, после 60 циклов закрытых окон Private Working Set — 18,3 МиБ. Дескрипторы не росли монотонно, но расход памяти был избыточным для текста и одной линии прогресса. Исходные результаты: `measurements/release-final`.

В итоговой версии используется **программный render target Direct2D** и DirectWrite. DWM по-прежнему управляет оформлением и композициeй окон. Это убирает необходимость отдельного GPU-контекста приложения и не создаёт постоянной GPU-отрисовки. На фоне Direct2D/DirectWrite вообще не создаются; после закрытия окна его ресурсы освобождаются. Принудительное урезание Working Set не применяется.

Отдельный стресс-тест `measurements/software-renderer`: после 200 циклов **Private Working Set 10,22 МиБ**, **Private Bytes 11,83 МиБ**, **GDI 16**, **USER 15**, **handles 224**. После прогрева при 20/60/100/200 циклах Private Bytes составляли 11,04/11,29/11,24/11,83 МиБ. Постоянного роста GDI/USER нет; небольшой рост выделений и резидентности не доказывает утечку и требует длительного наблюдения. Для сравнения взяты прогретые состояния, а не минимальный процесс до первой загрузки шрифтов и системных компонентов.

## Воспроизведение

```powershell
# Пять минут ожидания и 60 циклов окон
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\measure-performance.ps1 -IdleMinutes 5 -Cycles 60

# Точки в 5 и 30 минут плюс 200 циклов
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\measure-performance.ps1 -IdleMinutes 30 -Cycles 200
```

Сценарий сохраняет `metrics.csv`, `delivery.csv`, `environment.json` и тестовый профиль в новой папке `measurements`. В environment записываются SHA-256 EXE, версия ОС, число процессоров и времена запуска. Все файлы поставки учитываются отдельно. Скрипт опрашивает готовность только при запуске и затем снимает редкие контрольные точки; он не внедряет постоянный монитор в приложение.

Тридцатиминутное ожидание в этой сессии не измерялось; приведён готовый сценарий для него. Из нескольких циклов не следует отсутствие утечек на неделе работы. Нужны также ручные проверки разных DPI, мониторов, реального сна и блокировки из TEST_PLAN.md.
